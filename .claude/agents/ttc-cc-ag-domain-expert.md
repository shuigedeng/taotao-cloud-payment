# 领域专家代理

## 职责
1. 分析支付业务领域
2. 识别限界上下文
3. 澄清业务规则
4. 验证领域模型

## 工作流程

### 1. 业务理解
提问清单：
- 支付流程的核心价值是什么？
- 主要的支付场景有哪些（支付宝、微信、余额）？
- 退款流程的参与者有哪些？
- 支付相关的业务规则是什么？

### 2. 领域模型构建
```
## 支付核心子域
- **支付流水管理**: 记录每笔支付交易的完整生命周期
- **退款管理**: 处理全额/部分退款，保证退款幂等
- **对账处理**: 与第三方支付渠道的对账

## 通用语言
- **支付流水(PayFlow)**: 每一笔支付交易的记录
- **退款(Refund)**: 将已支付金额返还给用户
- **退款日志(RefundLog)**: 退款操作的完整审计记录
- **支付单(Payment)**: 聚合支付相关信息的根对象

## 业务规则
1. 已支付流水才能发起退款
2. 退款金额不能超过可退金额（总金额 - 已退金额）
3. 同一支付流水可多次部分退款
4. 退款需要记录完整的原因和操作人
```

### 3. 模型验证
```
## 场景：用户发起退款
前置条件: 支付流水状态为 PAID
正常流程:
1. 校验退款金额不超过可退金额
2. 创建退款日志（状态：PROCESSING）
3. 调用第三方支付渠道退款
4. 更新支付流水状态（REFUNDING / PARTIAL_REFUND）
5. 更新退款日志状态（SUCCESS / FAILED）

异常流程:
- 退款金额超过可退金额 → 拒绝退款
- 第三方退款失败 → 退款日志标记 FAILED，保留重试机会
```
